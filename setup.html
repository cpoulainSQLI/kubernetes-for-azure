Setup

Every lab in this course runs on a small Linux virtual machine (VM) in your own Azure subscription. This page gets the tools on your computer, clones the lab kit, builds the lab VM and the guardrails that protect your credit, and checks that everything the chapters need is in place. Read the Introduction first, in particular its section on costs.

What you will have at the end

  • The lab kit is cloned on your computer, with your settings in .env.
  • One command has built your lab environment from code: a lab VM reachable over SSH from your own public IP address only, a monthly budget with alerts, and a daily auto-shutdown.
  • The readiness report has no failed check, and you know which of its warnings matter before chapter 8.
  • You start the lab VM when you work and stop it when you finish.

Before you start

Accounts and tools

  • You need an Azure subscription where you have the Owner role. course up creates role assignments, which needs Owner (or User Access Administrator). A Visual Studio subscription with monthly credit fits, with the spending limit left on.
  • A GitHub account is optional. You only need one to fork the kit.
  • Your computer needs a terminal, the Azure CLI, Terraform 1.17.0 or later, Git and an OpenSSH client. On Windows, the course command runs in PowerShell, which is part of Windows. On macOS and Linux, it runs in bash.

What course up creates

One command, ./course up, builds the lab environment. This section explains what it creates and why, so that you know what you pay for.

Infrastructure as code with Terraform

course up creates the lab from Terraform files rather than from clicks in the portal. Terraform files are declarative: they describe the end state you want (a resource group, a budget, a VM with these settings), and Terraform works out what to create, change or delete to reach it. It talks to Azure through a provider, a plugin for one platform. Here that is the azurerm provider.

Terraform records what it created in a state, which maps each resource in the files to the real resource in Azure. Each run starts with a plan: Terraform reads the real resources, compares them and the files with the state, and lists the changes it proposes. course up prints that plan and asks you before it applies it. When nothing differs, the plan is empty and nothing changes.

The state has to outlive your computer, and two runs must never change it at the same time. So course up first creates a storage account in a resource group of its own, <PREFIX>-tfstate-rg, and Terraform keeps the state there, one blob for the setup and one per lab, with the azurerm backend. Terraform locks the state during a run. The account refuses account keys: you and the lab VM reach it with your Microsoft Entra ID identities and the Storage Blob Data Contributor role. Blob versioning keeps the earlier versions of the state, so a damaged state can be restored. The state lives outside the lab resource group, so deleting the lab never deletes the record of what it contained.

You will meet the same idea, describing the desired state and letting the platform converge, in chapter 2 with Kubernetes.

The files are in the setup/infra folder of the kit:

  • versions.tf sets the versions of Terraform and of the azurerm provider, and declares where the state lives.
  • variables.tf lists the settings that course up fills in from your .env file.
  • main.tf creates the resource group and the budget.
  • lab-vm.tf creates the network, the VM, the auto-shutdown schedule and the role assignments of the VM.
  • outputs.tf lists the values that Terraform prints at the end, such as the IP address of the VM.
  • .terraform.lock.hcl records the exact provider version and its checksums, so that every learner gets the same provider.
your public IP address changed and you run course up again. What does the second run do to the VM?

course up sees that the network rule no longer matches LEARNER_IP and runs Terraform. The plan shows one change, the source address of that rule. Terraform updates it and leaves the VM and its disk as they are, because they already match the files.

The kit on the lab VM

On its first boot, the VM runs cloud-init, a standard tool that configures a Linux machine from a file. The file, setup/infra/cloud-init.yaml, installs the tools of the labs:

  • Docker Engine is a container engine, the program that builds and runs containers. Chapter 1 explains what a container is.
  • kind runs a small Kubernetes cluster inside containers, for chapter 2.
  • kubectl is the command-line client of Kubernetes.
  • The Azure CLI lets the lab scripts work with Azure.
  • Terraform lets the labs create their Azure resources from the VM.

cloud-init then clones the kit into ~/aro-k8s-course and puts the course command on the PATH. It clones the same repository as your computer: course up reads the address of your clone with git remote get-url origin and turns it into an HTTPS address, because the VM clones without signing in. The setting KIT_REPO in .env overrides that address. After the VM is ready, course up checks the clone and copies your .env to it, and nothing else. Your own work on the VM goes in ~/work, outside the kit, so course update never touches it.

Reaching the lab VM safely

You connect with SSH, using a key pair instead of a password. The private key stays on your computer. The public key is copied to the VM when it is created, and password sign-in is turned off. Azure accepts RSA keys of at least 2048 bits and Ed25519 keys. SSH keys for Linux VMs

A network security group (NSG) filters traffic to the VM. The course adds one rule: TCP port 22 (SSH) is allowed from your public IP address with the suffix /32, which means that single address and nothing else. All other inbound traffic from the internet is denied by the default rules of every NSG. If your IP address changes, update LEARNER_IP in .env and run course up again. Network security groups

The VM also has a managed identity: an identity in Microsoft Entra ID that belongs to the VM itself. Scripts on the VM sign in with az login --identity, so no password or token is ever stored on the VM. The identity has three roles. Two are limited to the lab resource group: Contributor, so that lab scripts can create and delete their resources there, and AcrPush, so that you can push container images in chapter 1. The third, Storage Blob Data Contributor on the state storage account, lets Terraform on the VM keep the state of the labs. Chapter 4 comes back to why limiting the scope of a role matters. Managed identities

If your network blocks outgoing SSH, Azure Bastion Developer is a free alternative in many regions, including Sweden Central. It opens a terminal in your browser through the portal, without any public port, but it does not support native SSH clients or file copies, and allows one connection at a time. Bastion SKU comparison

why does the NSG rule end in /32, and what happens when you work from another network?

/32 limits the rule to exactly one IPv4 address. From another network, your public address is different, so the VM refuses the connection. Update LEARNER_IP in .env and run course up again.

Quotas, regions and resource providers

Azure limits how many vCPUs a subscription can run in a region, not every region offers every service, and a subscription has to register a service before it can use it. course up and the readiness report deal with all three for you, and the lab VM only needs 2 vCPUs. The report may still print warnings about quotas, because an ARO cluster needs far more in chapter 8. Nothing before then depends on them. Quotas, regions and resource providers explains each warning.

Get the kit

Clone the lab kit on your computer, in a folder of your choice. The commands are the same in PowerShell and in bash:

git clone https://github.com/<account>/kubernetes-for-azure-labs.git
cd kubernetes-for-azure-labs

To keep your own changes on GitHub, fork the kit first and clone your fork instead. Keep the fork public: the lab VM clones it without signing in. Every course command on this page runs from this folder.

Your settings

  1. Create an SSH key pair for the course, in your own .ssh folder. Never copy the private key anywhere else. A passphrase is recommended: you then type it when course connects to the VM, or load the key once into your SSH agent, as described in SSH keys for Linux VMs.

    New-Item -ItemType Directory -Force "$HOME\.ssh" | Out-Null
ssh-keygen -t ed25519 -f "$HOME\.ssh\aro-k8s-lab" -C aro-k8s-lab

    mkdir -p ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/aro-k8s-lab -C aro-k8s-lab

  2. Copy .env.example to .env in the kit folder and fill it in. At least set LEARNER_IP to your current public IPv4 address, which any "what is my IP" web page shows. Read the comment above each setting. Keep SSH_KEY_PATH=~/.ssh/aro-k8s-lab: the course command understands ~ on every platform. .env holds nothing secret, and Git ignores it.

    Copy-Item .env.example .env
notepad .env

    cp .env.example .env
open -e .env

    cp .env.example .env
nano .env

  3. On Windows only: allow scripts to run in this PowerShell window. Windows blocks scripts by default, and the command below only applies to the current window. If your organisation enforces another policy, the command reports it: ask your administrator, or run the bash version of course in Git Bash. About execution policies

    Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned

    Nothing to do. Git keeps the course command executable.

Create the lab environment

Sign in to Azure and check which subscription the CLI uses. If it is the wrong one, select the right one with az account set --subscription "<name>".

az login
az account show --query "{name:name, state:state}" --output table

Then, from the kit folder:

.\course.ps1 up

./course up

course up prints the estimated cost and asks for confirmation. It then registers the resource providers and creates the storage for the Terraform state. A new role can take up to 10 minutes to apply, so it may wait there on the first run. It prints the Terraform plan and asks again before it applies it. The first run downloads the azurerm provider, about 85 MB, to the .aro-k8s/terraform folder of your home folder, outside the kit. It then waits for SSH and for cloud-init, which takes 5 to 10 minutes on the first run, checks the kit on the VM and copies your .env there.

Once the lab VM exists, course up only starts it and checks the kit on it, which takes about a minute. When you change another setting of .env than LEARNER_IP, for example the budget, add --apply to run Terraform again.

Check that everything is ready

Run the readiness report from the kit folder. It changes nothing:

.\course.ps1 check

./course check

The setup is done when:

  • The readiness report has no [FAIL]. It covers your subscription, the region, the resource providers, the quotas, Terraform and its state, the budget and its alerts, the tags, the auto-shutdown, the network rule, the identity of the VM, the tools on the VM and the kit on the VM.
  • You can say, for each [WARN] in the report, whether it matters before chapter 8. Each warning comes with a hint that says what it means and when it matters.
  • You can open an SSH session on the lab VM with ./course connect, and run docker version, kind version, kubectl version --client and course help there. Type exit to leave.
  • You have found the budget in the portal (Cost Management, Budgets) and the auto-shutdown setting on the VM (Operations, Auto-shutdown), and you know at what time the VM shuts down.

Every session: start, work, stop

From now on, a working session always looks like this, from the kit folder on your computer:

.\course.ps1 up        # starts the lab VM, about a minute
.\course.ps1 connect   # SSH session on the lab VM, type exit to leave
.\course.ps1 stop      # deallocates the VM at the end of the session

./course up        # starts the lab VM, about a minute
./course connect   # SSH session on the lab VM, type exit to leave
./course stop      # deallocates the VM at the end of the session

In the SSH session, the course command runs the labs: course start 01, course check 01 and so on. course help lists them.

Always stop the VM with ./course stop, never with sudo poweroff from inside it: the Introduction explains why stopped is not the same as deallocated. ./course status shows the power state. The auto-shutdown deallocates the VM in the evening if you forget.

When the kit changes, ./course update pulls it on your computer, and on the lab VM if it runs. On the lab VM, course update does the same for its own clone.

Edit files from VS Code

The labs run on the lab VM, so the files you edit live there. In the SSH session you can use nano or vim. If you prefer VS Code, its Remote - SSH extension opens folders of the lab VM in VS Code on your computer. Whatever you open in that window runs on the VM: the files, the terminal and any extension you add there. Remote development using SSH

  1. In VS Code, install the extension Remote - SSH (ms-vscode-remote.remote-ssh).
  2. From the kit folder on your computer, run ./course ssh-config. It prints a Host block with the IP address of the lab VM, your user name, your key, and the known hosts file that ./course connect uses.
  3. Paste the block at the end of ~/.ssh/config on your computer (C:\Users\<you>\.ssh\config on Windows), and create the file if it does not exist. In PowerShell, .\course.ps1 ssh-config | Set-Clipboard puts the block on the clipboard.
  4. Start the VM with ./course up if it is stopped. Then, in VS Code, run "Remote-SSH: Connect to Host..." from the Command Palette and pick arok8s-lab-vm (the name starts with your PREFIX).
  5. Open the folder /home/azureuser/work, where course start puts the files of each lab. If you changed ADMIN_USERNAME, use your user name instead of azureuser.
  6. VS Code then offers the Kubernetes extension, which the course recommends for that folder. Install it. It goes on the lab VM, together with the YAML extension it depends on.

With the Kubernetes extension, VS Code completes and checks your manifests. It reads the apiVersion and kind of each document and takes the matching schema from the cluster that kubectl points to, so start a new manifest with those two fields. The kind configuration file is not a Kubernetes resource, so it gets no completion. Kubernetes extension for VS Code

In a terminal on the lab VM, in VS Code or in ./course connect, the Tab key completes kubectl and kind commands. ./course up sets this up, and it works in every new shell. Install kubectl on Linux

The first connection installs VS Code Server on the lab VM. Microsoft asks for at least 1 GB of memory on the remote machine and recommends 2 GB with a 2-core CPU. The lab VM has 2 vCPUs and 8 GiB. Linux prerequisites for remote development

The IP address in the block stays the same when you stop and start the VM. It changes only if you delete the environment with ./course destroy and create it again, and then you run ./course ssh-config again and replace the old block. VS Code loses the connection when the VM is deallocated, by ./course stop or by the auto-shutdown. Start the VM and reconnect.

Clean up and cost check

  • At the end of every session, deallocate the VM with ./course stop. Keep the environment, the chapters need it.
  • When you stop following the course for more than a few weeks, delete everything with ./course destroy. It runs terraform destroy, which deletes the resource group and the budget, then deletes the resource group of the Terraform state, and lists anything still tagged course=aro-k8s. If Terraform cannot finish, it deletes what is left with the Azure CLI. Azure may also have created a resource group called NetworkWatcherRG when the network was created. It has no cost on its own and you can keep it. Network Watcher
  • A day later, open Cost Management, Cost analysis, and filter on the tag course=aro-k8s. Costs appear with a delay of up to a day. For a one-hour session, expect well under 1 EUR.
