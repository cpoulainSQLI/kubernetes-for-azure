Style guide for contributors

How the courses are split, written, laid out, scripted, checked and published. These rules apply to every file of the website and of every lab kit, except the files in archive/ of the website, which are kept unchanged until they are reworked, and the frozen files in extras/ of a kit.

Repositories

The catalogue lives in one website repository and one lab kit repository per course. Learners follow the main branch of the kit of their course.

  • The website, kubernetes-hands-on, holds the pages of every course, their assets, the scripts that build and check them, the redirects, and the Terraform files of its own hosting. Learners never clone it.
  • Each course has its own kit, named after it with the pattern <course>-labs. The kit of course 1 is kubernetes-labs. A kit holds everything a learner of that course runs, and has its own course command, so that the commands of one course never touch another. Learners clone it, and a fork is optional.
  • A course with pages lives in courses/<name>/ of the website, and its kit is <name>-labs. The kit of a later course starts as a copy of the libraries of course 1.

A file that a learner runs, copies or edits belongs in the kit. A page that a learner reads belongs in the website. The checker of the website fails on any file of a kit left in the site.

The kit of course 1 is laid out like this:

PathContent
course, course.ps1The course command, in bash (Linux, macOS and the WSL distribution of the course) and in PowerShell (Windows)
.env.exampleTemplate of the optional settings, copied to .env, which Git ignores
setup/install-tools.sh, which installs the tools on Ubuntu or Debian, cloud-init.yaml and wsl-environment.sh, which build the WSL distribution, and the readiness report check.sh and check.ps1
labs/NN-name/setup.sh, validate.sh, teardown.sh, break.sh from chapter 1, and other files of the lab, such as its kind configuration
lib/lib.sh, lib.ps1, the staged validator engine lib-validate.sh and the broken lab engine lib-break.sh
sample-app/The Go code of the sample app
solutions/NN-name/The files of the reference solution, laid out like the work folder ~/work/NN-name
extras/Files kept apart from the main path, such as the frozen Azure lab VM. The course command does not use them
tools/check-kit.pyThe checker of the kit

The folder name NN-name is the same in labs/, in solutions/, in ~/work and in the website in courses/<name>/chapters/.

Writing

  • English with UK spelling (colour, behaviour, organise, licence as a noun) and metric units.
  • Headings in sentence case: only the first word and proper nouns take a capital letter.
  • No em dashes and no en dashes. Use a full stop, a comma, a colon or parentheses.
  • No semicolons in prose.
  • No bold text. Emphasis comes from the structure of the page, not from <strong> or <b>.
  • No "eg" in brackets. Write "for example".
  • Avoid filler words such as robust, seamless, tailored, foster, genuinely, leverage, crucial and delve.
  • In bulleted lists, write natural sentences, not "Title: content".
  • Explain every container and Kubernetes term the first time a chapter uses it. Do not explain Azure basics. Link to Microsoft Learn instead.
  • Paraphrase documentation and link to it. Do not copy documentation text.
  • Every product fact, limit and price is checked against primary documentation and cited in the Sources section of the page. Write "not verified" next to a statement that could not be checked.
  • Prices name their source, the currency, the region and the date of the lookup.
  • No file mentions a real person, an employer or a client. The learner, the subscription and the region are always variables.
  • Learner pages never mention how the website itself is hosted. This guide and the README of the website do.
  • Text that learners read stays a draft until the author has reviewed it.

Pages

The website is static HTML with no build step: open index.html in a browser, or let the deployment publish the pages as they are. Every page follows the same template.

  • The <body> element carries data-root, the relative path to the root of the website (for example ../../../../ for a chapter), and data-page, the path of the page from the root.
  • The page has the elements site-header, site-nav, main, page-toc and site-footer, in that order. assets/course.js fills the header, the navigation, the table of contents and the footer.
  • The navigation of each course is defined once, in the COURSES list at the top of assets/course.js, with the name of its kit. The pages shared by every course have their own short navigation there.
  • Headings that should appear in the table of contents are h2 and h3 elements with an id.
  • After any change to the text, run python3 scripts/build-lab-sheets.py, then python3 scripts/build-search-index.py, to update the lab sheets and assets/search-index.js.

The home page is the catalogue. Each course is a card with what you learn, what you should know before, where it runs, its time, its cost and its status. A course that has pages has a folder courses/<name>/ with its own home page (index.html, with the outline), introduction.html, setup.html, chapters, solutions and sample app pages. The Introduction explains the course, the website and the kit, and how a lab works. The Setup page takes the learner from an empty computer to an environment that passes the readiness report. About, Resources, the Azure limits and this guide are shared.

When a page moves, its old address gets a permanent redirect in staticwebapp.config.json. The checker fails when a redirect hides a page that still exists or leads to one that does not.

Commands and links to the kit

  • A page shows course commands, never the path of a script. Commands that build the environment from the kit folder are written ./course up, with .\course.ps1 up as their PowerShell form. Commands that run in the environment are written course start 01, course check 01 --guided and so on. The checker fails when a page shows a command, a lab or an option that the kit of its course does not have.
  • A link to a file of the kit is an <a> element without href, with the path of the file in the kit in data-kit: <a data-kit="setup/install-tools.sh">. A folder ends with a slash, and data-kit="." is the whole kit. The checker fails when the path does not exist in the kit of the course of the page. Shared pages link to the kit of course 1.
  • assets/course.js turns these elements into links to the kit of the course on GitHub. assets/kit.js names the account that hosts the kits. The deployment writes that file, and it is never committed. Without it, for example on a page opened from disk, the links show <account> in their address, and a short note at the top of the page says why.
  • An element with a data-kit-owner attribute gets <account> in its text replaced by the same account, for example the git clone command of a Setup page.

Chapter structure

The chapters of course 1 are being rebuilt in a new form: a short landing page and section pages, read in order. This guide describes that form once the first chapter is rebuilt. Until then, each chapter is one page, courses/<name>/chapters/NN-name/index.html, with these sections in this order:

  1. What you will be able to do: 3 to 5 observable outcomes.
  2. Before you start: prerequisites, time needed, and the cost of the lab when it has one.
  3. Concepts: short sections, with a diagram where it helps. Each section ends with a check-yourself question: a <details class="check-yourself"> element whose summary holds the question and whose body holds the answer.
  4. Knowledge check: 5 multiple-choice questions in an <ol class="quiz"> list. Each question carries its answer in data-answer and its explanation in a <details> element, which the script opens once the learner checks an answer.
  5. Lab: goal, numbered tasks with two hints each, acceptance criteria grouped by stage, the course start, course check and course clean commands of the lab, how the validation works, and the broken lab.
  6. Clean up.
  7. Sources, with links to primary documentation.

A chapter never contains a copy-paste solution to its lab. The files of a reference solution live in the kit, in solutions/NN-name, and course solution NN copies them into the work folder after asking. The website explains each solution on a page in courses/<name>/solutions/NN-name/index.html.

Under each task, two <details class="hint"> elements give help in two steps. The first says where to look. The second gives the shape of the answer, with placeholders in place of the learner's own values.

The time needed is an estimate until someone has measured it. course up, the lab setup scripts and the guided check print how long they took, so a test run gives the numbers to write there.

Each chapter has a lab sheet, lab-sheet.html, with the Lab and Clean up sections alone on one page. scripts/build-lab-sheets.py generates it from the chapter page, so never edit it by hand.

Platform variants

Only the commands that build and manage the environment differ between Windows (PowerShell) and Linux or macOS (bash). Every lab runs in one Linux shell, the environment, which is the WSL distribution of the course on Windows and the machine itself on Linux.

  • A block with variants is a <div class="tabs"> that holds one <div class="tab-panel"> per variant. Each panel has a data-label, shown on its tab, and a data-os list with one or more of windows, macos and linux. Together the panels cover the three. The script shows the panel that matches the computer chosen in the header, and remembers the choice.
  • An inline command with a PowerShell form is written <code data-ps="PowerShell form">bash form</code>, for example <code data-ps=".\course.ps1 check">./course check</code>. The script swaps the text when the learner chooses Windows.
  • A block that runs in the environment is preceded by <p class="where">In the environment (bash)</p>.

Diagrams

Diagrams are drawn in Claude Design, on one canvas that holds one artboard per diagram. The canvas is the working copy. Pages embed an export of each artboard: a PNG file in assets/diagrams/, at twice the size of the artboard, inside a <figure class="diagram"> element.

  • An artboard is 880 pixels wide, so that the text keeps its size in the page. It uses the colours of the site (ink #242424, grey #616161, blue #0f6cbd for the one element the diagram is about) and the Inter typeface at 16 pixels, 13 pixels for labels.
  • Boxes are separate elements and each arrow is its own small drawing, so that anyone can move or retype a part on the canvas.
  • A solid arrow is something that happens in the chapter. A dashed arrow is something that happens later or on a schedule.
  • The <img> element carries the width and height of the artboard and an alt text that says what the diagram shows.
  • After a change on the canvas, export the artboard again and replace the PNG file.

Labs

Every lab has four parts in the kit, in labs/NN-name: a setup script, a validation script and a teardown script, plus the tasks and acceptance criteria on the chapter page. Nothing else reviews the learner's work, so the validation script checks every acceptance criterion that a script can check.

  • The learner runs them through the course command in the environment: course start NN runs setup.sh, course check NN runs validate.sh, course break NN runs break.sh and course clean NN runs teardown.sh. A new lab needs no change to course: it finds the folder by its number.
  • course start NN is the one command a learner runs when a lab begins and every time they come back. It creates what is missing, starts what has stopped, waits until it is ready, and ends with course check NN --next, which says which task is next. It is safe to run any number of times and never throws work away.
  • Each lab that needs a cluster has its own kind cluster, and one cluster runs at a time. lab_cluster_up in lib/lib.sh creates it, records the lab it belongs to, starts its stopped node containers, and connects it to the registry. When the cluster of another lab exists, it asks whether to clean that lab first.
  • The registry on localhost:5001 belongs to the environment, not to a lab. course up creates it with a named volume, course clean NN never removes it, and course destroy removes it with the rest. From chapter 2 on, the nodes pull from it, and no lab uses kind load.
  • The learner's own files live in ~/work/NN-name, outside the clone of the kit, so that course update never touches them.
  • Lab scripts run in the environment and are bash only.

The course command

On Windows, course.ps1 builds and manages the WSL distribution of the course: up, connect, status, check, stop, destroy and update. In the environment, the bash course runs the same commands of the environment and the commands of the labs: start, check NN, break, solution and clean. On Linux the environment is the machine itself, so ./course in the kit folder does both.

  • The two lines ENV_COMMANDS and LAB_COMMANDS of course list the commands. Both checkers read them, and course.ps1 accepts every command of the environment.
  • Every name derives from the name of the kit, KIT_NAME in lib/lib.sh and $KitName in lib/lib.ps1: the WSL distribution, the clone in it, the kind cluster and its context, the registry and its volume. tools/check-kit.py fails when they disagree.
  • Every course command prints the name of its course on its first line.
  • On Windows, course up writes the user data of cloud-init in the .cloud-init folder of the Windows profile, creates the distribution from stock Ubuntu with wsl --install --no-launch, and lets cloud-init create the user learner, run setup/install-tools.sh and setup/wsl-environment.sh, clone the kit and put a launcher on the path. It never edits the learner's .wslconfig.
  • On Linux, course up lists the tools it would install and asks before it runs setup/install-tools.sh with sudo. It then offers a launcher in ~/.local/bin, and names the kit of a launcher that is already there before it replaces it. On macOS it installs nothing.
  • On Linux, connect and stop answer in one line, and destroy removes only what belongs to the course. On Windows, destroy deletes the distribution and says that ~/work goes with it.
  • The clone URL of the distribution comes from git remote get-url origin of the learner's clone, turned into HTTPS, or from KIT_REPO in .env. No file names the account that hosts the kit.
  • course update runs git pull --ff-only.

Validation scripts

From chapter 1 onwards, a validator sources lib/lib-validate.sh and is cut into stages, one per task of the lab, in the same order.

  • Each stage is a function, stage_N, that prints only through check_pass, check_fail, check_warn, check_skip and check_note. A second function, stage_N_task, prints the task in a few lines for the guided mode, without the solution.
  • A validator defines WORK_DIR. When that folder does not exist, course check NN stops with one message that says to run course start NN. A lab with a cluster does the same when its cluster does not answer.
  • Every stage holds for the finished lab, so that the full report passes at the end, and never fails because of a later task.
  • Checks read what the learner wrote (the Dockerfile, the YAML files) as well as the result (the image, the registry, the cluster). A check on a file names the line to change in its hint.
  • A [FAIL] is an acceptance criterion of the chapter page that is not met. A [WARN] is something that works but should be improved. The page lists both.
  • Without an option the script is read-only. Tests that create, change or delete something are live tests: they run only with --deep, stay inside the environment and the kind cluster, and clean up after themselves. Without --deep they print [SKIP].
  • --guided walks the stages one at a time. It keeps no state: it reads the work each time and resumes at the first stage that does not pass. --next prints that stage alone.
  • The checker of the website compares the number of stages with the tasks of the chapter page.

Broken labs

From chapter 1 onwards, a lab is followed by a broken lab: labs/NN-name/break.sh sources lib/lib-break.sh, puts one fault into the finished lab and lets the learner find it.

  • A fault changes only what lives in the environment or in the kind cluster, never the learner's files and never the registry. The script says what it changes and asks before it does.
  • Each fault has three functions: symptom_NAME prints what a user would report, inject_NAME injects it, and explain_NAME says how to see it and what repairs it. An optional break_preflight stops the script when the lab cannot be broken, for example when its cluster is down.
  • The diagnosis question lists one cause per fault, plus causes that are never the answer.
  • course break NN --restore always puts the lab back as it was, and the validator of the chapter must fail on every fault. The chapter page presents that command.

Scripts

Bash

  • Start with set -euo pipefail and source lib/lib.sh.
  • The course command and setup/check.sh may run on a Mac, so they stay compatible with bash 3.2, the version that ships with macOS: no associative arrays, no mapfile, no timeout command. Scripts that only run in the environment on Linux can rely on the bash of Ubuntu.
  • Run another script of the kit with bash script.sh, so that it works even when Git did not keep its executable bit. Commit every script with the executable bit anyway: git update-index --chmod=+x on Windows.

PowerShell

  • Dot-source lib/lib.ps1, which sets Set-StrictMode -Version Latest and $ErrorActionPreference = 'Stop'.
  • Stay compatible with Windows PowerShell 5.1, which ships with Windows. PSScriptAnalyzer checks the syntax against 5.1 and 7.4.
  • Call native programs through Invoke-Native and Invoke-Wsl, which check exit codes and hide the error stream of read-only calls.
  • Run a command in the distribution with Invoke-InDistro, which uses wsl --exec so that no other shell reads it first. Never put double quotes in that command: Windows PowerShell 5.1 drops them. Send a longer script with Invoke-InDistroScript, which carries it in base64.
  • Write ${Name} when a variable is followed by a question mark or a colon in a string: PowerShell reads $Name? as one variable.

Rules for both

  • Every parameter comes from .env, which is optional. Nothing is hard-coded per learner.
  • Safe to run twice: a second run updates or skips, it never fails because something already exists.
  • Scripts for the learner's computer exist in bash and in PowerShell with the same # check: <id> and # step: <id> comments: course and course.ps1, setup/check.sh and setup/check.ps1. tools/check-kit.py fails when a pair does not have the same IDs.
  • Validation scripts are read-only unless the learner adds --deep. They print [PASS], [FAIL] or [WARN] per check, with a hint after each failure, and exit with 0 when nothing fails and 1 otherwise.
  • Scripts never print tokens, keys or passwords, and never take a password on the command line.
  • Tool versions are pinned in lib/lib.sh, lib/lib.ps1, setup/install-tools.sh and the kind configuration of each lab. Docker Engine is not pinned: the readiness report prints its version.

Azure resources

Course 1 creates no Azure resource. The rules below apply to the courses that run on Azure, and they still describe the frozen files in extras/azure-lab-vm/ of the kit of course 1.

  • Every resource created by Terraform or by a script of a kit carries a tag that names the course and a chapter=NN tag, where NN is the two-digit chapter number, and 00 for the setup. In Terraform, each resource sets tags = local.tags.
  • A resource type that cannot carry tags (budgets, role assignments, subnets) is preceded in Terraform by a comment that starts with # untaggable: and says why.
  • Clean-up commands end by listing everything still tagged for the course.
  • The shared Azure setup of those courses (subscription, budget, quotas, regions, resource providers, Terraform state) is written once, when the first of them is designed.

Hosting of the website

The website is an Azure Static Web Apps resource on the Free plan, in the author's subscription. Learners never host it.

  • The Terraform files are in infra/, with every value a variable. They create their own resource group, tagged component=site and with a project tag of its own, never with the tag of a course, so that the clean-up commands of a kit never list or delete it.
  • The state is a local file under the user profile, outside every repository and outside any synchronised folder, because it holds the deployment token. The README of the website gives the commands.
  • The region is West Europe. On 16 November 2026 the resource type accepted Central US, East US 2, West US 2, West Europe and East Asia, not Sweden Central, according to az provider show --namespace Microsoft.Web. The content is served globally anyway: the region only hosts managed Functions and staging environments. Static Web Apps FAQ
  • The Free plan includes 100 GB of bandwidth a month and 250 MB per environment, allows 10 apps per subscription, and has no SLA. Quotas, plans
  • The site keeps the *.azurestaticapps.net hostname that Azure generates. Pull request preview environments are off, in Terraform with preview_environments_enabled = false.
  • staticwebapp.config.json at the root of the published folder holds the redirects: one route per old address, with redirect and statusCode 301. An exact route to index.html also matches the address of its folder. The file is limited to 20 KB. Configure Azure Static Web Apps
  • The workflow .github/workflows/deploy.yml runs on every push. It checks out the kit of each course next to the website, at the branch of the same name when it exists and at main otherwise, and runs the checks. On main only, it then writes assets/kit.js from github.repository_owner and uploads the pages with Azure/static-web-apps-deploy and skip_app_build: true. Work that is not ready to publish stays on a branch. The deployment token is in the repository secret AZURE_STATIC_WEB_APPS_API_TOKEN. Build configuration, deployment tokens

Personal data

No file contains a subscription ID, a tenant ID, a public IP address, an e-mail address or a secret. Private address ranges (for example 10.20.0.0/16) and the IDs of Azure built-in roles are allowed, because they are the same for everyone.

Checks

Run these from the root of the website before publishing a change. The two build scripts come before the checker, which fails when a lab sheet or the search index is stale.

npx html-validate "**/*.html"
terraform fmt -check -recursive infra
terraform -chdir=infra init -backend=false -input=false > /dev/null && terraform -chdir=infra validate
python3 scripts/build-lab-sheets.py
python3 scripts/build-search-index.py
python3 scripts/check-course.py

scripts/check-course.py checks the writing rules in every page, the internal links and anchors, the alternative text of images, the personal data rules, the tags of the hosting, the redirects, the search index and the lab sheets. It also reads the kit of each course, <name>-labs, in the parent folder of the website or in KITS_DIR, and checks that the stages of each validator match the tasks of its page, that every course command a page shows exists, and that every data-kit path exists. To also search for names that must never appear (your own name, an employer, a client), put them in the PRIVATE_TERMS environment variable, separated by commas. Never write them in a file.

Run these from the kit folder before a change to the kit, then run the checker of the website again:

shellcheck -x course setup/*.sh labs/*/*.sh lib/*.sh
pwsh -c "Invoke-ScriptAnalyzer -Path . -Recurse -Settings ./PSScriptAnalyzerSettings.psd1"
(cd sample-app && go vet ./... && go test ./...)
python3 tools/check-kit.py

tools/check-kit.py checks the personal data rules, the names derived from the kit name, the pinned tool versions, the parity between the bash and PowerShell scripts, the structure of the validators and broken labs, and the executable bit of the scripts in the Git index. It also takes PRIVATE_TERMS. Each repository has a workflow that runs its checks on GitHub.

The scripts that build the environment are tested by hand: course up on each platform, and course start NN after a stop of the environment.
