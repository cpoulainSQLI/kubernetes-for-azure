Style guide for contributors

How the course is split, written, laid out, scripted, checked and published. These rules apply to every file of both repositories except the files in archive/, which are kept unchanged until they are reworked.

Repositories

The course lives in two Git repositories that learners follow on their main branch.

  • The website, kubernetes-for-azure, holds the pages, their assets, the scripts that build and check them, and the Terraform files of its own hosting. Learners never clone it.
  • The lab kit, kubernetes-for-azure-labs, holds everything a learner runs. Learners clone it, and the lab VM clones it too. A fork is optional.

A file that a learner runs, copies or edits belongs in the kit. A page that a learner reads belongs in the website. The checker of the website fails on any file of the kit left in the site.

The kit is laid out like this:

PathContent
course, course.ps1The course command, in bash (your computer and the lab VM) and in PowerShell (your computer)
.env.exampleTemplate of the learner settings, copied to .env, which Git ignores
setup/The lab VM: Terraform files and cloud-init in setup/infra, the readiness report check.sh and check.ps1, and kit-on-vm.sh, the lab VM side of course up
labs/NN-name/setup.sh, validate.sh, teardown.sh, break.sh from chapter 1, other files of the lab, and the Terraform files of the lab in infra
lib/lib.sh, lib.ps1, the staged validator engine lib-validate.sh and the broken lab engine lib-break.sh
sample-app/The Go code of the sample app
solutions/NN-name/The files of the reference solution, laid out like the work folder ~/work/NN-name of the lab VM
tools/check-kit.pyThe checker of the kit

The folder name NN-name is the same in labs/, in solutions/, on the lab VM in ~/work and in the website in chapters/.

Writing

  • English with UK spelling (colour, behaviour, organise, licence as a noun) and metric units.
  • Headings in sentence case: only the first word and proper nouns take a capital letter.
  • No em dashes and no en dashes. Use a full stop, a comma, a colon or parentheses.
  • No semicolons in prose.
  • No bold text. Emphasis comes from the structure of the page, not from <strong> or <b>.
  • No "eg" in brackets. Write "for example".
  • Avoid filler words such as robust, seamless, tailored, foster, genuinely, leverage, crucial and delve.
  • In bulleted lists, write natural sentences, not "Title: content".
  • Explain every container and Kubernetes term the first time a chapter uses it. Do not explain Azure basics. Link to Microsoft Learn instead.
  • Paraphrase documentation and link to it. Do not copy documentation text.
  • Every product fact, limit and price is checked against primary documentation and cited in the Sources section of the page. Write "not verified" next to a statement that could not be checked.
  • Prices name their source, the currency, the region and the date of the lookup.
  • No file mentions a real person, an employer or a client. The learner, the subscription and the region are always variables.
  • Learner pages never mention how the website itself is hosted. This guide and the README of the website do.

Pages

The website is static HTML with no build step: open index.html in a browser, or let the deployment publish the pages as they are. Every page follows the same template.

  • The <body> element carries data-root, the relative path to the root of the website (for example ../../), and data-page, the path of the page from the root.
  • The page has the elements site-header, site-nav, main, page-toc and site-footer, in that order. assets/course.js fills the header, the navigation, the table of contents and the footer.
  • The navigation is defined once, in the NAV list at the top of assets/course.js.
  • Headings that should appear in the table of contents are h2 and h3 elements with an id.
  • After any change to the text, run python3 scripts/build-lab-sheets.py, then python3 scripts/build-search-index.py, to update the lab sheets and assets/search-index.js.

The Introduction (introduction.html) explains the course, the two repositories, how a lab works and what the course costs. The Setup page (setup.html) takes the learner from an empty computer to a lab VM that passes the readiness report. The home page keeps the outline and one line about the total cost.

Commands and links to the kit

  • A page shows course commands, never the path of a script. On the learner's computer that is ./course up, with .\course.ps1 up as its PowerShell form. On the lab VM it is course start 01, course check 01 --guided and so on. The checker fails when a page shows a command, a lab or an option that the kit does not have.
  • A link to a file of the kit is an <a> element without href, with the path of the file in the kit in data-kit: <a data-kit="labs/01-containers/infra/main.tf">. A folder ends with a slash, and data-kit="." is the whole kit. The checker fails when the path does not exist in the kit.
  • assets/course.js turns these elements into links to the kit on GitHub, from assets/kit.js, which names the account that hosts the kit. The deployment writes that file, and it is never committed. Without it, for example on a page opened from disk, the links show <account> in their address, and a short note at the top of the page says why.
  • An element with a data-kit-owner attribute gets <account> in its text replaced by the same account, for example the git clone command of the Setup page.

Chapter structure

Each chapter is one page, chapters/NN-name/index.html, with these sections in this order:

  1. What you will be able to do: 3 to 5 observable outcomes.
  2. Before you start: prerequisites, time needed, estimated cost of the lab.
  3. Concepts: short sections, with a diagram where it helps. Each section ends with a check-yourself question: a <details class="check-yourself"> element whose summary holds the question and whose body holds the answer.
  4. Knowledge check: 5 multiple-choice questions in an <ol class="quiz"> list. Each question carries its answer in data-answer and its explanation in a <details> element, which the script opens once the learner checks an answer.
  5. Lab: goal, numbered tasks with two hints each, acceptance criteria grouped by stage, the course start, course check and course clean commands of the lab, how the validation works, and the broken lab.
  6. Clean up and cost check.
  7. Sources, with links to primary documentation.

The chapter page never contains a copy-paste solution to the lab. The files of a reference solution live in the kit, in solutions/NN-name, and course solution NN copies them into the work folder after asking. The website explains each solution on a page in solutions/NN-name/index.html.

Under each task, two <details class="hint"> elements give help in two steps. The first says where to look. The second gives the shape of the answer, with placeholders in place of the learner's own values.

The time needed is an estimate until someone has measured it. course up, the lab setup scripts and the guided check print how long they took, so a test run gives the numbers to write there.

Each chapter has a lab sheet, lab-sheet.html, with the Lab and Clean up sections alone on one page. scripts/build-lab-sheets.py generates it from the chapter page, so never edit it by hand.

Platform variants

Commands that run on the learner's computer differ between Windows (PowerShell) and macOS or Linux (bash). Commands that run on the lab VM are always bash.

  • A block with variants is a <div class="tabs"> that holds one <div class="tab-panel"> per variant. Each panel has a data-label, shown on its tab, and a data-os list with one or more of windows, macos and linux. The script shows the panel that matches the computer chosen in the header, and remembers the choice.
  • An inline command with a PowerShell form is written <code data-ps="PowerShell form">bash form</code>, for example <code data-ps=".\course.ps1 stop">./course stop</code>. The script swaps the text when the learner chooses Windows.
  • A block that runs on the lab VM is preceded by <p class="where">On the lab VM (bash)</p>.

Diagrams

Diagrams are drawn in Claude Design, on one canvas that holds one artboard per diagram. The canvas is the working copy. Pages embed an export of each artboard: a PNG file in assets/diagrams/, at twice the size of the artboard, inside a <figure class="diagram"> element.

  • An artboard is 880 pixels wide, so that the text keeps its size in the page. It uses the colours of the site (ink #242424, grey #616161, blue #0f6cbd for the one element the diagram is about) and the Inter typeface at 16 pixels, 13 pixels for labels.
  • Boxes are separate elements and each arrow is its own small drawing, so that anyone can move or retype a part on the canvas.
  • A solid arrow is something that happens in the chapter. A dashed arrow is something that happens later or on a schedule.
  • The <img> element carries the width and height of the artboard and an alt text that says what the diagram shows.
  • After a change on the canvas, export the artboard again and replace the PNG file.

Labs

Every lab has four parts in the kit, in labs/NN-name: a setup script, a validation script and a teardown script, plus the tasks and acceptance criteria on the chapter page. Nothing else reviews the learner's work, so the validation script checks every acceptance criterion that a script can check.

  • The learner runs them through the course command on the lab VM: course start NN runs setup.sh, course check NN runs validate.sh, course break NN runs break.sh and course clean NN runs teardown.sh. A new lab needs no change to course: it finds the folder by its number.
  • The learner's own files live in ~/work/NN-name on the lab VM, outside the clone of the kit, so that course update never touches them.
  • Lab scripts run on the lab VM and are bash only.

The course command

On the learner's computer, course (bash) and course.ps1 (PowerShell) manage the lab environment: up, connect, status, check, stop, destroy and update. On the lab VM, the bash course runs the labs: start, check, break, solution, clean and update. The marker file /etc/aro-k8s/lab-vm tells the two sides apart.

  • The two lines LAPTOP_COMMANDS and VM_COMMANDS of course list the commands of each side. Both checkers read them.
  • course up is safe to run twice. When the lab VM exists and its network rule matches LEARNER_IP, it only starts the VM. Otherwise, or with --apply, it runs Terraform. It then makes sure that the kit is cloned on the lab VM and copies .env there, and only .env.
  • cloud-init clones the kit into ~/aro-k8s-course on the first boot and installs a launcher, /usr/local/bin/course. The clone URL comes from git remote get-url origin of the learner's clone, turned into HTTPS, or from KIT_REPO in .env. No file names the account that hosts the kit.
  • course update runs git pull --ff-only.

Validation scripts

From chapter 1 onwards, a validator sources lib/lib-validate.sh and is cut into stages, one per task of the lab, in the same order.

  • Each stage is a function, stage_N, that prints only through check_pass, check_fail, check_warn, check_skip and check_note. A second function, stage_N_task, prints the task in a few lines for the guided mode, without the solution.
  • Every stage holds for the finished lab, so that the full report passes at the end, and never fails because of a later task.
  • Checks read what the learner wrote (the Dockerfile, the YAML files) as well as the result (the image, the cluster). A check on a file names the line to change in its hint.
  • A [FAIL] is an acceptance criterion of the chapter page that is not met. A [WARN] is something that works but should be improved. The page lists both.
  • Without an option the script is read-only. Tests that create, change or delete something are live tests: they run only with --deep, stay inside the lab VM and the kind cluster, clean up after themselves, and never touch an Azure resource. Without --deep they print [SKIP].
  • --guided walks the stages one at a time. It keeps no state: it reads the work each time and resumes at the first stage that does not pass.
  • The checker of the website compares the number of stages with the tasks of the chapter page.

Broken labs

From chapter 1 onwards, a lab is followed by a broken lab: labs/NN-name/break.sh sources lib/lib-break.sh, puts one fault into the finished lab and lets the learner find it.

  • A fault changes only what lives on the lab VM or in the kind cluster, never the learner's files and never an Azure resource. The script says what it changes and asks before it does.
  • Each fault has three functions: symptom_NAME prints what a user would report, inject_NAME injects it, and explain_NAME says how to see it and what repairs it.
  • The diagnosis question lists one cause per fault, plus causes that are never the answer.
  • course break NN --restore always puts the lab back as it was, and the validator of the chapter must fail on every fault. The chapter page presents that command.

Scripts

Bash

  • Start with set -euo pipefail and source lib/lib.sh.
  • The course command and setup/check.sh run on the learner's computer and stay compatible with bash 3.2, the version that ships with macOS: no associative arrays, no mapfile, no timeout command. Scripts that only run on the lab VM can rely on the bash of Ubuntu.
  • Run another script of the kit with bash script.sh, so that it works even when Git did not keep its executable bit. Commit every script with the executable bit anyway: git update-index --chmod=+x on Windows.

PowerShell

  • Dot-source lib/lib.ps1, which sets Set-StrictMode -Version Latest and $ErrorActionPreference = 'Stop'.
  • Stay compatible with Windows PowerShell 5.1, which ships with Windows. PSScriptAnalyzer checks the syntax against 5.1 and 7.4.
  • Call native programs through the helpers of lib.ps1 (Invoke-Native, Get-AzJson, Get-AzValue, Invoke-AzChange), which check exit codes and hide the error stream of read-only calls.
  • Never pass JSON on a command line. Windows PowerShell 5.1 drops the quotes inside it. Write a temporary parameters file instead.
  • Read JSON from az with Get-Prop, which returns nothing instead of failing when a property is missing.

Rules for both

  • Every parameter comes from .env. Nothing is hard-coded per learner.
  • Safe to run twice: a second run updates or skips, it never fails because something already exists.
  • Scripts for the learner's computer exist in bash and in PowerShell with the same # check: <id> and # step: <id> comments: course and course.ps1, setup/check.sh and setup/check.ps1. tools/check-kit.py fails when a pair does not have the same IDs.
  • Validation scripts are read-only unless the learner adds --deep. They print [PASS], [FAIL] or [WARN] per check, with a hint after each failure, and exit with 0 when nothing fails and 1 otherwise.
  • Scripts never print tokens, keys or passwords, and never take a password on the command line.
  • SSH keys are created on the learner's computer and never written to a repository.

Azure resources of the labs

  • Every resource created by Terraform or by a script of the kit carries the tags course=aro-k8s and chapter=NN, where NN is the two-digit chapter number, and 00 for the setup. In Terraform, each resource sets tags = local.tags.
  • A resource type that cannot carry tags (budgets, role assignments, subnets) is preceded in Terraform by a comment that starts with # untaggable: and says why.
  • The setup keeps its Terraform files in setup/infra, and a lab that creates Azure resources keeps its own in labs/NN-name/infra: versions.tf with the versions, an empty azurerm backend block and the provider settings, the resources, and the committed .terraform.lock.hcl.
  • The state lives in the storage account that course up creates, in the container tfstate: one blob for the setup, setup.tfstate, and one per lab named after its folder. Scripts pass the backend settings with terraform init -backend-config and reach the account with Microsoft Entra ID, never with an account key.
  • Scripts pass values to Terraform through TF_VAR_ environment variables, and set TF_DATA_DIR to ~/.aro-k8s/terraform/<setup or lab folder>, so that no Terraform working file lands in the kit.
  • On the lab VM, Terraform signs in with the managed identity of the VM, and the provider never registers resource providers: course up registers them.
  • Clean-up commands end by listing everything still tagged course=aro-k8s.

Hosting of the website

The website is an Azure Static Web Apps resource on the Free plan, in the author's subscription. Learners never host it.

  • The Terraform files are in infra/, with every value a variable. They create their own resource group, tagged project=kubernetes-for-azure and component=site. The website never carries the tag course=aro-k8s, so that the clean-up commands of the kit never list or delete it.
  • The state is a local file under the user profile, outside both repositories and outside any synchronised folder, because it holds the deployment token. The README of the website gives the commands.
  • The region is West Europe. On 16 November 2026 the resource type accepted Central US, East US 2, West US 2, West Europe and East Asia, not Sweden Central, according to az provider show --namespace Microsoft.Web. The content is served globally anyway: the region only hosts managed Functions and staging environments. Static Web Apps FAQ
  • The Free plan includes 100 GB of bandwidth a month and 250 MB per environment, allows 10 apps per subscription, and has no SLA. Quotas, plans
  • The site keeps the *.azurestaticapps.net hostname that Azure generates. Pull request preview environments are off, in Terraform with preview_environments_enabled = false, and in the workflow, which only runs on main.
  • The workflow .github/workflows/deploy.yml checks out the kit next to the website, runs the checks of the website, writes assets/kit.js from github.repository_owner, then uploads the pages with Azure/static-web-apps-deploy and skip_app_build: true. It deploys only if every check passes. The deployment token is in the repository secret AZURE_STATIC_WEB_APPS_API_TOKEN. Build configuration, deployment tokens

Personal data

No file contains a subscription ID, a tenant ID, a public IP address, an e-mail address or a secret. Private address ranges (for example 10.20.0.0/16) and the IDs of Azure built-in roles are allowed, because they are the same for everyone.

Checks

Run these from the root of the website before publishing a change. The two build scripts come before the checker, which fails when a lab sheet or the search index is stale.

npx html-validate "**/*.html"
terraform fmt -check -recursive infra
terraform -chdir=infra init -backend=false -input=false > /dev/null && terraform -chdir=infra validate
python3 scripts/build-lab-sheets.py
python3 scripts/build-search-index.py
python3 scripts/check-course.py

scripts/check-course.py checks the writing rules in every page, the internal links and anchors, the alternative text of images, the personal data rules, the tags of the hosting, the search index and the lab sheets. It also reads a checkout of the kit, in the sibling folder ../kubernetes-for-azure-labs or in KIT_DIR, and checks that the stages of each validator match the tasks of its page, that every course command a page shows exists, and that every data-kit path exists. To also search for names that must never appear (your own name, an employer, a client), put them in the PRIVATE_TERMS environment variable, separated by commas. Never write them in a file of the course.

Run these from the kit folder before a change to the kit, then run the checker of the website again:

shellcheck -x course setup/*.sh labs/*/*.sh lib/*.sh
pwsh -c "Invoke-ScriptAnalyzer -Path . -Recurse -Settings ./PSScriptAnalyzerSettings.psd1"
terraform fmt -check -recursive
for d in setup/infra labs/*/infra; do terraform -chdir="$d" init -backend=false -input=false > /dev/null && terraform -chdir="$d" validate; done
(cd sample-app && go vet ./... && go test ./...)
python3 tools/check-kit.py

tools/check-kit.py checks the personal data rules, the tags, the pinned tool versions, the parity between the bash and PowerShell scripts, the structure of the validators and broken labs, and the executable bit of the scripts in the Git index. It also takes PRIVATE_TERMS.

terraform init -backend=false downloads the provider without reaching the state. It leaves a .terraform folder next to the files, which Git ignores and the checkers skip, unless TF_DATA_DIR points elsewhere. Each repository has a workflow that runs its checks on GitHub.
